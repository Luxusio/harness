# Bytecode cache cannot disable receipts

Related: [[REQ__receipt-subsystem-failures-are-observable]],
[[REQ__harness-announces-lost-receipt-capability]],
[[REQ__receipt-capability-diagnosis]].

## The mechanism

CPython's default `.pyc` invalidation is timestamp-based: it compares the
header's recorded mtime and size against the `.py` and nothing else. A cache
whose header matches but whose bytecode does not is therefore accepted for as
long as it sits on disk. Python will never recompile it.

Verified in the live tree on 2026-09-16
(`~/.claude/harness-dev/plugin/scripts/__pycache__`):

```
pyc header mtime : 1789381586   .py mtime: 1789381586   -> equal
pyc header size  : 32362        .py size : 32362        -> equal
invalidation flags: 0 (timestamp-based)
cached code == fresh compile of the .py : False
```

Six of seven `cpython-312` caches in that tree were header-valid and
content-mismatched: `subagent_lifecycle`, `_lib`, `codex_lifecycle_watcher`,
`codex_hook_registration`, `hook_tree_health`, `runbook_memory`.

The consequence is total and silent. `subagent_lifecycle` binds its receipt
adapter at import time; the guard in `_lib` compares the loaded code object
against a fresh compile of the file and refuses on mismatch; `background_hook`'s
single import block therefore raises, the hook calls `sys.exit(0)`, and **every
subsequent hook reports success while writing nothing**. `doc/harness/learnings.jsonl`
carried 23 `receipt-subsystem-unavailable` entries between 2026-09-07 and
2026-09-16 before the cause was identified.

## Why install-time pruning was not enough

`install.py:_prune_bytecode_caches` already existed, already named this exact
failure in its docstring, and was already wired at three call sites — each
deliberately **before** the staleness decision, because payload comparison lists
`__pycache__` in `_VOLATILE_DIR_NAMES` and a poisoned tree still answers
SYNCHRONIZED to `--if-stale`.

That remains correct and stays. It is insufficient because it is install-time
only: pruning happens, hooks re-import, caches are rewritten, and any later
divergence re-poisons a tree that no longer gets reinstalled. Cleanup timing
can always lose that race. The class has to be removed rather than swept.

## The requirement

1. **Prevention.** Every process that imports from an installed `scripts/` tree
   runs with `PYTHONDONTWRITEBYTECODE=1`, so none of them can create a cache
   that could later go stale. "Hook commands" alone is not the boundary — that
   framing is what made the first attempt at this fix miss the actual writers.
   The full launcher set, all covered:

   | Launcher | Where |
   |---|---|
   | Claude hook commands (9) | `plugin/hooks/hooks.json` |
   | Codex hook commands (4) | generated by `install.py:_codex_hooks_config` |
   | Codex MCP server, TOML | `install.py:_mcp_block` — the one Codex launches |
   | Codex MCP server, JSON | `install.py:_codex_mcp_config` |
   | Claude MCP server, dev install | `install.py` `env_args` for `claude mcp add` |
   | Claude MCP server, marketplace plugin | `plugin/.mcp.json` — shipped in the payload, not registered by `install.py`, so installer-scoped checks are blind to it |
   | `scripts/*.py` invocations documented for an agent to run | `plugin/**`, `plugin-codex/**`, `doc/harness/patterns/**`, `README.md`, `README.codex.md` — enumerated and enforced by `test_documented_script_invocations_also_disable_bytecode`, which is the authority for both the root set and the count |

   The importer sets overlap, so no single launcher explains the observed
   caches: `_lib` is imported by seven hook commands, by the MCP server, and by
   most `scripts/*.py` entrypoints; `codex_hook_registration` and
   `codex_lifecycle_watcher` by the generated Codex hook entrypoints and the MCP
   server; `hook_tree_health` by the MCP server. Coverage is applied to every
   launcher rather than to whichever one seemed responsible.

   C-12 is unaffected: each hook command still ends with `|| true` and keeps
   `timeout <= 10`.

2. **Naming.** The receipt-adapter guard distinguishes the benign shape — every
   identity and filesystem predicate passes and only the comparisons against a
   fresh compile fail — from tampering, and raises `StaleBytecodeCacheError`
   with the cause and the remedy. **Both branches still refuse.** The split
   changes the error's identity, never the decision: an attacker who swaps the
   `.py` after a good import lands in the same half and is still rejected.
   Widening what binds would be a security regression and is not the goal.

3. **Recovery.** On **any** import failure `background_hook` removes the
   `__pycache__` beside itself, so the next invocation recompiles and records.
   Not only on the named shape: a poisoned `_lib` cache surfaces as
   `ImportError: cannot import name ...`, which never reaches the guard that
   raises `StaleBytecodeCacheError`, so a gate on that name left the commonest
   module in the tree uncovered. The asymmetry settles it — a needless prune
   costs one recompile of a directory Python regenerates anyway, a missed prune
   costs every receipt until a human notices. Which shape it was is still
   recorded, as diagnostics.
   Bounded exactly like the installer's prune: one `__pycache__`, only inside
   the tree the script already lives in, real directories only, symlinks
   rejected before removal.

4. **Honest capability.** A failing hook writes
   `doc/harness/.receipt-capability-broken`; a healthy import removes it. The
   MCP reads that marker and reports `receipts_recordable: false` with the
   recorded cause. This is an observation written by the process that actually
   failed, not an inference from plugin registration — which is why it is a
   definite `false` rather than the `None` that `receipt_capability_warning`
   correctly earns. It is evaluated **before** the `_run_has_receipts`
   override, because earlier receipts in the same run do not disprove a break
   that happened after them.

## Why this matters more than the outage itself

The detection must be checked by the same run that relies on it. On 2026-09-16
`task_start` reported `receipts_recordable: true` for a subsystem that was
incapable of writing a single receipt. On that assurance a full review lane and
a full QA lane were spawned and completed, and only afterwards did the empty
receipt stream surface — costing the entire task and ending in a park. A
capability signal that cannot observe the capability is worse than no signal,
because it is trusted.

## Checkable statement

- No launcher in the table above invokes `python3` against an installed
  `scripts/` tree without `PYTHONDONTWRITEBYTECODE=1` — hook commands, both MCP
  registrations, and the documented `scripts/*.py` invocations alike.
- A hook import failure prunes the sibling `__pycache__` whatever the exception
  shape, not only when it names a stale cache.
- A module whose loaded code differs from a fresh compile, with every other
  guard predicate passing, raises `StaleBytecodeCacheError`; any other predicate
  failure raises the original refusal.
- Two consecutive hook invocations against a poisoned tree end with the cache
  pruned, the marker cleared, and the receipt recorded.
- With the marker present, `task_start` reports `receipts_recordable: false`.
