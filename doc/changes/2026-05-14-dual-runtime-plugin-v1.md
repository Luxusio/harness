The v1 dual-runtime harness plugin ships the foundational infrastructure for running the harness under OpenAI Codex CLI alongside Claude Code. Nine of twelve acceptance criteria are delivered: Codex hook payload deltas are captured in a 13-pattern `apply_patch` vs `Edit` matrix (`doc/harness/apply-patch-matrix.md`, `doc/harness/codex-payload-deltas.md`); the environment variable `CLAUDE_PLUGIN_ROOT` is renamed to `HARNESS_PLUGIN_ROOT` with a one-version dual-name fallback (all 15+ call sites updated, sunset documented in `CHANGELOG.md`); all four gate scripts (`prewrite_gate.py`, `mcp_bash_guard.py`, `qa_delegation_gate.py`, `stop_gate.py`) now emit structured `type=gate-crash` JSON to `learnings.jsonl` when payload parsing fails under `|| true` fail-safe, ending silent gate disablement under Codex payload drift; the Codex CLI version pin is established at `plugin-codex/.codex-version` (0.130.0); a runtime capability matrix at `doc/harness/runtime-matrix.md` documents per-feature Claude vs Codex support; the `plugin/.claude-plugin/plugin.json` `features` block and `marketplace.json source=./plugin` together implement an opt-in/opt-out model so existing Claude users see no change by default; and the full Codex doc surface ships (`README.codex.md`, `plugin-codex/README.md`, `plugin-codex/config.toml.example`, `doc/harness/codex-troubleshooting.md` with 11 structured error entries). Three ACs (3-skill hand-port spike, sharability canonical-form decision, and shared MCP config.toml emitter) are deferred to the follow-up task `TASK__dual-runtime-v1.5-spike-and-sync` because they require empirical `codex exec` runs and depend on the spike-first data that v1 infrastructure was designed to enable.
